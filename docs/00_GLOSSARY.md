# 00 · 术语表

先把这个文档里会出现的东西解释清楚。全部用大白话，不绕弯子。看不懂某个词就回来查。

---

## 一、文件与容器

**AssetBundle**
Unity 把资源（贴图、模型、音频、场景……）打成一个包，这种包叫 AssetBundle。游戏运行时按需加载。
你看到的每一个 `cab-xxxxxxxx` 都是它的内部名字。

**UnityFS**
AssetBundle 的一种具体格式，也是现代 Unity 唯一还在用的格式。文件头是字符串 `UnityFS`。
本项目的所有包都是 UnityFS v8。

**SerializedFile**
UnityFS 包里面装的东西。一个包可以塞多个 SerializedFile，每个里面又是一堆对象（Texture2D、
Mesh、TextAsset……）。AssetRipper 干的事就是把这些对象一个个拆出来。

**node / 节点**
UnityFS 的目录项。每个 node 描述"这个包里有这么一份文件，叫这个名字，从数据区的第几字节开始，
多长"。相当于 zip 里的中央目录。

**block / 数据块**
UnityFS 把整个包的数据切成若干块，每块单独压缩。这样加载时可以只解一块，不用全解。
块表记录每块的"解压后大小 / 压缩后大小 / 压缩方式"。

**data_start**
数据区的起始绝对偏移。等于 `blocksInfo` 结束位置向上补齐到 16 的倍数。
同一个游戏里不同包的 `data_start` 不一样，因为 `blocksInfo` 长度不同——这个差异后面非常重要。

## 二、压缩

**LZ4 / LZ4HC**
一种极快的压缩算法。分成很多"序列"（sequence），每个序列是：

```
[token] [额外长度字节...] [若干原样字节(literal)] [2字节offset] [额外的匹配长度字节...]
```

`token` 一个字节，高 4 位 = 原样字节数，低 4 位 = 匹配长度减 4。
如果高 4 位是 15，说明"还有更多"，后面跟一串 255 直到不满 255 为止。
offset 是"往回退多少字节开始复制"。

**关键性质**：解析这个结构时，**原样字节本身的内容不参与解析**。只有 token、长度扩展字节、
offset 这三个东西决定结构走向。原样字节的内容随便是什么都行。

这一点是本项目的核心突破口：加密只改变了字节内容，没有改变结构走向，所以可以"顺着结构走，
顺便反推密钥"。

**stored / 未压缩块**
块表里 flags 的低 6 位如果是 0，表示这块没压缩，原样存放。本项目里这类块**也被加密了**。

**LZMA**
另一种压缩算法，压缩率更高但更慢。本游戏的包里没用到，代码里留了处理分支。

## 三、加密

**XOR**
按位异或。`a ^ b ^ b = a`。所以用同一串密钥异或两次就回到原文。流式加密最常用的手法。

**keystream（密钥流）**
一串和文件一样长的伪随机字节。加密就是 `密文[i] = 明文[i] ^ 密钥流[i]`。
本游戏的密钥流不是随机数生成器产生的，而是由"base"和"每文件 key"两个东西拼出来的。

**base（基础密钥）**
一段短字节串，本游戏是 **11 字节**。它决定密钥流的"底色"。

**key / asset_key（每文件密钥）**
一个 64 位有符号整数，每个文件不一样。它写在游戏的 manifest 里。

**周期**
密钥流每 `8 × len(base)` 字节重复一次。11 × 8 = **88 字节**。

**明文区 / 密文区**
本游戏的文件，`[0x00, 0x100)` 这 256 字节是明文，`[0x100, 文件末尾)` 是密文。
分界线固定在 `0x100`，和包的结构无关。

**GF(2) / 有限域**
只有 0 和 1 两个数的算术，加法就是异或，乘法就是与。因为在 GF(2) 上，XOR 是线性的，
所以"已知密文、未知密钥"可以写成线性方程组，用高斯消元解。

**高斯消元**
解线性方程组的标准方法：把方程排成矩阵，一行一行消掉未知数，最后回代求出每个未知数。
本项目用它来判断"这组方程有没有解"，以及解出 base 的各个比特。

**零空间 / 自由变量**
方程组如果有多个解（约束不够），那些"可以自由取值"的变量构成零空间。
本项目里 base 有 8 个比特是自由的，所以有 2^8 = 256 个候选解，逐个用 LZ4 校验挑出真的。

**已知明文攻击**
如果知道明文的一部分，就能直接算出对应位置的密钥流，进而推出密钥。
本项目里 98.3% 的包在 `0x100` 之前就开始放数据，所以数据开头的几十字节**本来就是明文**，
天然构成已知明文。

## 四、清单

**manifest**
游戏用来记录"有哪些资源、每个资源是什么版本、大小多少"的清单文件。
本游戏的 manifest 里**还存着每个文件的 key**，这是关键。

**MasterMemory**
日本社区常用的一个 C# 内存数据库/序列化库，manifest 的表结构就是它定义的。

**msgpack**
一种紧凑的二进制序列化格式。manifest 用 msgpack 打包，一个接一个对象连着写，最后跟 16 字节 MD5。

**Ext99**
msgpack 的"扩展类型 99"。MasterMemory 用它标记 `DateTime` 之类的特殊值。
解析器不注册这个类型会直接抛异常。

**TOC（Table of Contents）**
manifest 开头的目录，记录每张表的数据从文件第几字节开始、多长。注意这里的 offset 是
**相对于 TOC 结束位置**的，不是相对于文件开头。

## 五、其它两种容器

**AKPK**
Audiokinetic Package 的缩写，Wwise 音频中间件的打包格式。魔数是 `AKPK`。
里面是一串 chunk：`BKHD`（头）、`DIDX`（索引）、`DATA`（数据）、`HIRC`（事件）。

**Wwise**
Audiokinetic 出的音频中间件，游戏行业用得极多。它的音频文件叫 `.wem`，本质是 RIFF WAV 的变体。

**WEM**
Wwise Encoded Media。看起来是 RIFF/WAVE，但里面的编码可能是 Vorbis、ADPCM、PCM 等，
而且 Vorbis 用的是**私有码本布局**，标准 Vorbis 解码器解不了。

**BKHD / DIDX / DATA / HIRC**
AKPK 里的四种 chunk。`DIDX` 是索引表，每条 12 字节：`id(4) + offset(4) + size(4)`，
offset 相对于 DATA 数据区起点。`HIRC` 是事件/容器定义。

**CRID / USM**
CRI 中间件的视频容器。文件头魔数 `CRID`，扩展名一般是 `.usm`。
里面是一串块：`@UTF`（元数据）、`@SFV`（视频）、`@SFA`（音频）、`@END`（结束）。

**Sofdec**
CRI 的视频编解码器品牌名。Sofdec 出过好几代：MPEG-1 基础的、H.264 的、VP9 的。
本游戏的 346 个视频里，326 个是 VP9，20 个是 MPEG-1。

**IVF**
一个极简的视频容器，专门用来装 VP8/VP9。文件头是 `DKIF`，后面每帧是
`[4字节长度][8字节时间戳][帧数据]`。

**ADX**
CRI 自己的音频编码，4 位 ADPCM。文件头是 `80 00`。

**Annex-B**
H.264 / MPEG-1 裸流的字节流格式，用 `00 00 01` 或 `00 00 00 01` 作为每个 NAL 单元的分隔符。
没有容器，没有时间戳，只有一帧接一帧的压缩数据。

## 六、工具

**AssetRipper / AssetStudio**
两个开源的 Unity 资源提取工具。输入一个 `.ab`（或整个目录），输出贴图、模型、脚本等。
它们**不认识**本游戏的加密，所以直接喂原始文件会失败——这正是本项目的起点。

**UnityPy**
纯 Python 写的 Unity 资源读取库，和 AssetRipper 是独立的两套实现。
本项目用它来做交叉验证：如果两套独立实现都能读出对象，那结果基本可以认为是对的。

**vgmstream**
一个开源音频解码库/命令行工具，支持几百种游戏音频格式，包括 Wwise 的各种变体。
本项目用它把 `.wem` 解成 `.wav`。

**ffmpeg**
万能音视频工具。本项目用它：
* 把拆出来的 MPEG-1 / H.264 裸流封装或转码成 `.mp4`；
* 把 VP9 的 `.ivf` 转成 `.mp4`；
* 解码 ADX 音轨并与视频合流。

**WPF**
Windows 的桌面 UI 框架，.NET 自带。本项目的图形界面用它写。

## 七、本项目自造的词

**明文模板 / 模板池**
从"已知密钥的文件"里采集出来的、特定偏移上的 8 字节明文片段集合。
用途：对未知密钥的文件，用模板反推出密钥（详见 `docs/03_WALKTHROUGH.md` 第 8 节）。

**反推密钥**
在拿不到 manifest 条目时，从密文和已知的 base 倒推出该文件的 `int64` key。

**跨界 blocksInfo**
`blocksInfo` 的起点在 `0x30` 附近，如果它比较长，就会跨过 `0x100` 这条线，
尾段变成密文。这种包如果不先解密 `blocksInfo` 尾段，LZ4 一定失败——
本项目最初有 2 297 个包因此被静默跳过。
