# 10 · 桌面程序

这一篇讲 `src/SZB_Asset_Decryption.App` 的界面结构、各页面职责，以及按钮事件的处理流程，
并记录实现过程中遇到的问题。

前面 01～09 讲格式与解析方法，本篇讲界面实现。

---

## 一、三层结构，为什么这么分

```
src/
├─ SZB_Asset_Decryption.Core/   解析与还原的全部逻辑（无界面依赖）
├─ SZB_Asset_Decryption.Cli/     命令行外壳
└─ SZB_Asset_Decryption.App/     WPF 界面外壳
```

`Core` 里没有一行 WPF 代码。这样做的直接好处是：命令行和界面跑的是同一份实现，
不存在"界面能过、命令行过不了"这种两套逻辑对不上的情况。

`Core` 的五个主要类：

| 类 | 负责什么 | 文档 |
|---|---|---|
| `UnityFsBundle` | 读容器头、块表、节点表 | `01_UNITYFS_FORMAT.md` |
| `XorKeystream` | 生成密钥流并就地异或 | `02_ENCRYPTION.md` |
| `AssetManifest` | 解析 manifest，查 key | `05_MANIFEST.md` |
| `AkpkPackage` | 拆 Wwise 音频包 | `06_AUDIO.md` |
| `UsmFile` | 拆 CRI 视频容器 | `07_VIDEO.md` |

`App` 这一层只做三件事：**接收参数、后台执行任务、回传进度**。

## 二、界面的六个页面

左侧导航固定六项，一件事一页：

| 序号 | 页面 | 做什么 | 入口方法 |
|---|---|---|---|
| 01 | 概览 | 选目录、读清单、跑只读体检 | `OverviewView.RunCensus_Click` |
| 02 | 资源还原 | 去 XOR 层，输出 `.ab` 树 | `AssetView.RunAsync` |
| 03 | 音频 | 拆 `.pck` → `.wem` → `.wav` | `AudioView.RunAsync` |
| 04 | 视频 | 拆 `.usm` → `.mp4` | `VideoView.RunAsync` |
| 05 | 设置 | 并发数、密钥推导、依赖状态 | `SettingsView` |
| 06 | 关于 | 边界说明与第三方组件 | `AboutView` |

### 为什么"目录"放在概览页而不是设置页

它是**前置条件**，不是偏好。不选目录则无法执行任何操作，因此放在首屏而非设置页。
设置页只放行为开关：并发数、密钥推导、依赖，这些在选完目录后才会用到。

选完数据目录后，如果输出目录还是空的，程序会自动填一个同级目录 `SZB_Restored`。
这一步很小，但它让"选完目录立刻能点开始"成立。

### 密钥行：一个值，三个按钮

设置页的密钥区说明该值的来源：

| 控件 | 行为 |
|---|---|
| 当前密钥 + 明细行 | 显示 hex 和"依据"：多少字节、周期、用了多少包、多少对同明文、秩多少 |
| 计算 | 从本地文件推导（约 20 秒）。已有缓存时几十毫秒 |
| 重新计算 | 忽略缓存重新推导 |
| 手动指定 + 应用 | 粘贴 hex/base64 直接指定 |

推导的每一步都进日志，包括扫了多少文件、配出多少对、每个长度是不是自洽。所以失败时能看出
卡在哪一步，而不是只得到一句"失败了"。

密钥为空时，「开始还原」会触发一次推导；仍为空则不执行。

> **并发问题：** 启动时推导已开始，用户此时点「开始还原」，任务页不能带着空密钥执行。
> `DeriveBaseKeyAsync` 用锁保证**重叠调用共享同一 Task**，后到的调用等待结果而非被拒绝。
> 第一版未处理，表现为还原任务立即报错退出，而日志显示推导进行中。

详细算法见 [`11_BASE_KEY_SOLVER.md`](11_BASE_KEY_SOLVER.md)。

## 三、"开始还原"的调用链

这部分结构简单，但容易写错。完整调用链：

```
AssetView.Start_Click()
  └─ RunAsync(limit)                          ← 组装参数
       ├─ RestoreOptions { DatRoot, OutputRoot, Manifest, BaseKey, ..., Cancellation }
       ├─ new Progress<RestoreProgress>(p => { 更新进度条 / 统计块 })   ← 在 UI 线程创建
       └─ await Task.Run(() => {
              svc.EnumerateBundles()          ← 扫目录，IO，必须在后台
              svc.Run(progress, files)        ← Parallel.ForEach 内部自己开线程
          })
```

三个关键点：

**1. `Progress<T>` 必须在 UI 线程创建。**

`Progress<T>` 在构造时抓取当前的 `SynchronizationContext`，之后每次 `Report()`
都把回调投递回那个上下文。所以它必须 `new` 在按钮事件里（UI 线程），
不能 `new` 在 `Task.Run` 里面——那样回调会落在没有消息循环的线程池线程上，
更新控件时抛 `The calling thread cannot access this object`。

**2. 枚举文件也要放进后台。**

`EnumerateBundles()` 要遍历 1024 个子目录，冷启动时能卡几百毫秒。
如果它在 `await` 之前同步执行，界面会先白一下。所以它和 `Run()` 一起被 `Task.Run` 包住，
通过 `subset` 参数把结果传回 `Run()`，避免扫两遍。

**3. 取消是协作式的。**

`CancellationToken` 只在 `Parallel.ForEach` 的调度点和每个包的开头被检查。
点取消之后，正在处理的那几个包会先把当前这个包写完才停。
所以取消后的日志写的是"已请求取消，正在收尾"，不是"已取消"——这是故意的，
词要对得上实际行为。

界面上的 `finally` 块负责把按钮状态恢复：

```csharp
finally
{
    SetBusy(false);      // 按钮恢复、进度条归零、取消按钮隐藏
    _cts?.Dispose();
    _cts = null;
}
```

没有这段，任何一次异常都会让"开始"按钮永久灰掉。

## 四、共享状态只有一个对象

六个页面要读同一批东西：数据目录、输出目录、清单、基础密钥、并发数、运行日志。
如果每页各存一份，就会出现"在概览改了目录，还原页还拿着旧的"这种问题。

所以只有一个 `Workspace`（`Services/Workspace.cs`），单例，实现 `INotifyPropertyChanged`。
页面用 `x:Static` 直接绑定到它，**不通过 DataContext 继承**：

```xml
<TextBox Text="{Binding DatRoot, Source={x:Static svc:Workspace.Current}}" />
```

为什么不用 DataContext？因为 `LogPanel` 是嵌在别的页面里的 UserControl，
父级一旦设置 `DataContext`，会把子级的继承覆盖掉。用 `x:Static` 指死源头，
不管外面怎么套都不会失联。

`Workspace` 里还有一个细节：

```csharp
public void Append(LogLevel level, string text)
{
    var app = Application.Current;
    if (app?.Dispatcher is { } d && !d.CheckAccess())
    {
        d.BeginInvoke(() => Append(level, text));   // 后台线程 → 跳回 UI 线程
        return;
    }
    Log.Add(new LogEntry { ... });
    while (Log.Count > 2000) Log.RemoveAt(0);       // 上限 2000 行
}
```

日志会从工作线程被调用（比如每处理 64 个包上报一次），所以它自己判断线程，
不要求调用方操心。上限 2000 行用于控制内存占用：36 673 个包各占一行会使 `ObservableCollection` 拖慢界面。

## 五、设置存在哪

`%LOCALAPPDATA%\SZB_Asset_Decryption\settings.json`，纯 JSON，打开就能改：

```json
{
  "DatRoot": "E:\\...\\Persistent\\dat",
  "OutputRoot": "E:\\WB_restored",
  "Parallelism": 8,
  "VerifyBlocks": false,
  "CopyWhenKeyMissing": false
}
```

每次改动写一次，数据量很小，无需防抖。读取时 `PropertyNameCaseInsensitive = true`，
手工改大小写也能认。

注意这里**没有密钥**。密钥不写在设置里，因为它是算出来的，不是配置值——写进来就成了
一个会过期的副本。算出来的结果单独放在 `base-key.json`，那边记着"凭什么算出来的"
（清单路径、大小、时间），清单一变就作废。理由写在 `02_ENCRYPTION.md` 第 10 节。

## 六、依赖查找顺序

`External/ToolLocator.cs` 按固定顺序探测，**排在前面的一定赢**：

1. 程序目录下的 `Dependencies\`
2. 程序目录下的 `deps\`
3. 程序目录下的 `tools\bin\ffmpeg\bin`、`tools\bin\vgmstream`、`tools\bin`
4. 从程序目录往上最多 6 层，每层试一遍上面三个相对路径（为了 `src/SZB_Asset_Decryption.App/bin/Release/net10.0-windows` 能找到仓库根的 `tools/bin`）
5. 最后才回落到 `PATH`

顺序不能反。若先查 `PATH`，用户机器上的旧版 ffmpeg 会覆盖随程序打包的版本，
导致输出异常且难以定位。**随程序打包的版本必须优先**是这里唯一的设计原则。

## 七、实现中遇到的问题

以下每一条都是实际遇到并修正的。

### 问题 1：`StartupUri` 和截图模式不能共存

`App.xaml` 里写 `StartupUri="MainWindow.xaml"` 时，WPF 会在 `OnStartup` **返回之后**
自己创建一个主窗口。如果 `OnStartup` 里想干别的事（比如截图模式），就会凭空多出一个窗口。

改法：删掉 `StartupUri`，在 `OnStartup` 里手动 `new MainWindow()` + `Show()`。
多两行，但控制权在自己手里。

### 问题 2：TabControl 自带的页签无法隐藏

想用 `TabControl` 做页面容器（因为它自带"只显示选中项"的逻辑），但不想显示那一排页签。
只改 `TabItem` 的样式不够，页签是 `TabControl` 模板里的 `TabPanel` 画的。

改法：直接换掉 `TabControl` 的模板，只留一个内容呈现器：

```xml
<TabControl.Template>
  <ControlTemplate TargetType="TabControl">
    <ContentPresenter ContentSource="SelectedContent" />
  </ControlTemplate>
</TabControl.Template>
```

`ContentSource="SelectedContent"` 是关键字——它让呈现器去读 `TabControl.SelectedContent`，
而不是 `Content`。

### 问题 3：自绘标题栏后按钮无响应

用 `WindowChrome` 自绘标题栏（`CaptionHeight="46"`）之后，标题栏那 46 像素整块被当成
"非客户区"，鼠标事件被窗口管理器拦截，最小化/关闭按钮无法点击。

改法：给按钮容器加一个附加属性。

```xml
<StackPanel shell:WindowChrome.IsHitTestVisibleInChrome="True">
```

拖拽和双击最大化由 `WindowChrome` 提供，不必自己写 `DragMove()`。

### 问题 4：`Loaded` 触发多次导致日志重复

第一版跑起来，日志里"依赖检查通过"出现了两遍。

原因：`TabControl` 在选中内容时会重新挂载 `ContentPresenter` 的内容，
`Loaded` 因此被触发第二次。任何"只在初始化时做一次"的事情（写日志、预加载清单）
都会做两遍。

改法：加标志位。

```csharp
private bool _initialised;

private void OnLoaded(object sender, RoutedEventArgs e)
{
    if (_initialised) return;
    _initialised = true;
    ...
}
```

该问题不易察觉：界面表现正常，只有日志重复，容易误判为日志写入逻辑错误。

### 问题 5：截图背景全黑

程序提供 `--shot` 模式，用 `RenderTargetBitmap` 把窗口内容渲染为 PNG。
结果出来的图里，卡片和文字都在，**卡片之间的背景是纯黑**。

原因：`RenderTargetBitmap.Render(visual)` 只渲染你给它的那棵视觉树。
窗口的 `Background` 画在 `Window` 上，而 `Window.Content`（我传进去的根 `Border`）
自己没设背景，于是那块是透明的，导出成不透明 PNG 就变黑了。

改法：给根 `Border` 显式设背景。

```xml
<Border Background="{StaticResource BgBase}" ...>
```

这条对真实窗口没影响（`Window.Background` 会兜底），但任何离屏渲染都会暴露它。

### 问题 6：进度条不可见

进度条轨道色原为 `#1A2233`，卡片背景为 `#151C2B`，两者差值过小，
未填充时进度条不可见。

改法：轨道提到 `#232E44`（`Themes/Dark.xaml` 里的 `Bar` 样式）。
深色界面中，对比度不足会导致控件不可见。

### 问题 7：枚举名出现在用户界面文案中

日志里出现了：

```
开始转换动画，输出格式 Mp4H264。
```

`Mp4H264` 是 `VideoContainer` 的枚举名，被 `$"{container}"` 直接插进了字符串。
开发时看没问题，用户看到的是内部标识符。

改法：加一层显示名映射，日志写 `MP4 · H.264`。

```csharp
private static string DescribeContainer(VideoContainer c) => c switch
{
    VideoContainer.Mp4Copy => "MP4 · 直接封装",
    VideoContainer.MkvCopy => "MKV · 直接封装",
    _ => "MP4 · H.264",
};
```

**教训**：所有 `$"{someEnum}"` 插值都要确认是否会出现在用户界面。

## 八、截图模式兼作冒烟测试

`SZB_Asset_Decryption.exe --shot <目录>` 会做这些事：

1. 建主窗口，挪到屏幕外（`Left = -30000`），`Show()` 但用户看不见；
2. 逐页 `SelectPage(i)` → 等布局和绑定跑完 → `RenderTargetBitmap` 存 PNG；
3. 带 `--run` 时，先在三个任务页各跑一个小任务（还原 12 个、音频 2 个、视频 1 个），
   走的是和按钮**完全一样**的代码路径；
4. 关窗退出。

两个用途：

* **生成 README 的截图**，不需要人工摆好界面再截屏；
* **当冒烟测试用**。任何一页的 XAML 写错（资源键拼错、绑定路径不存在、
  事件处理器没实现），这一步会直接抛异常，而不是等到用户点开才发现。

跑完的真实输出（可作为参考基线）：

| 项目 | 结果 |
|---|---|
| 还原 | 12/12 成功，3.75 MiB，59 ms |
| 音频 | 2 个包，2 个 wem，2 个 wav，1.6 s |
| 视频 | 1 个动画（去重跳过 199 个），2.2 s，输出 h264 1920×1080 30fps 5.70 s |
| 校验 | 12 个 `.ab` 用 UnityPy 逐个加载全部通过，共 1 831 个对象 |

## 九、已知限制

* **取消不是硬中断。** 点了取消，正在写的包会写完再停。要真正秒停，得在 `RestoreOne`
  内部按块检查 token，代价是每个块的循环里多一次判断。
* **没有断点续跑。** 中途退出，下次会从头开始。判断"这个文件已经还原过"需要额外记状态，
  而 `restore` 全量约几分钟，暂不实现。
* **日志上限 2000 行**，超出的旧行会被丢弃。跑全量时早期日志会滚掉。
* **界面不显示对象级内容。** 它只负责还原成合法容器，对象解析由 AssetRipper 处理。
* **仅支持 Windows。** 这是 WPF 的限制，非设计选择。
