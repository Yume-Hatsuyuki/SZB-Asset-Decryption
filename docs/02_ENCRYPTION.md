# 02 · 加密算法

这一章把加密写成可以照着实现的规格。看完你应该能自己写一份解密器。

---

## 1. 定义

从文件绝对偏移 `0x100` 开始，每一个字节都和密钥流做一次 XOR：

```
cipher[o] = plain[o]                ,  o <  0x100
cipher[o] = plain[o] ^ ks[o]        ,  o >= 0x100
```

`o` 是**绝对文件偏移**（从文件第一个字节数起），不是相对数据区的偏移，也不是相对 `data_start` 的偏移。
这一点必须记牢，写错就一定解不出来。

---

## 2. 密钥流

```
period = 8 × len(base)                       // 本项目 base 长 11 字节 → period = 88
i      = o mod period                        // o 为绝对偏移
ks[o]  = base[i >> 3] ^ key_le[i & 7]
```

* `base` 是一段短的字节串，**对所有文件相同**
* `key` 是每个文件不同的 64 位有符号整数
* `key_le[j]` 是 `key` 按**小端**存放时的第 `j` 个字节，即 `(byte)(key >> (8*j))`
* `>>` 是整数右移，`&` 是按位与

等价写法（C#）：

```csharp
static byte KeyStreamByte(ReadOnlySpan<byte> baseKey, long key, long absoluteOffset)
{
    int period = baseKey.Length * 8;
    int i      = (int)(absoluteOffset % period);
    byte kb    = (byte)(key >> (8 * (i & 7)));
    return (byte)(baseKey[i >> 3] ^ kb);
}
```

---

## 3. 本游戏的实际参数

| 参数 | 值 |
|---|---|
| 明文区长度 | `0x100`（256 字节） |
| `base` | 11 字节，本次分析（2026-11 版本）解出的是 `53 2b 46 31 e4 a7 b9 47 3e 7c fb` |
| `len(base)` | 11 |
| `period` | 88 |
| `key` | 每个文件一个 `int64`，见 `docs/05_MANIFEST.md` |

上面这个 `base` 是**当时那一版**的值，不是永恒常量：游戏更新后它会变，换版本再套旧值解出来的是
一堆能过结构检查、但内容全错的包。所以工具不把它编进程序——启动时从一个 URL 拉取（见
`README.md` 的"Where the base key comes from"），拿不到就留空并拒绝还原。

`base` 的 base64 表示是 `UytGMeSnuUc+fPs=`（同样只对那一版有效）。

---

## 4. 密钥流字节的来源

把 88 字节的密钥流摊开，看每个字节受什么影响：

| 周期内位置 i | 用到的 base 字节 | 用到的 key 字节 |
|---|---|---|
| 0 | `base[0]` | `key` 第 0 字节 |
| 1 | `base[0]` | `key` 第 1 字节 |
| … | … | … |
| 7 | `base[0]` | `key` 第 7 字节 |
| 8 | `base[1]` | `key` 第 0 字节 |
| 9 | `base[1]` | `key` 第 1 字节 |
| … | … | … |
| 87 | `base[10]` | `key` 第 7 字节 |

**结论：`key` 的第 `j` 个字节，只影响周期内位置 ≡ `j (mod 8)` 的那些密钥流字节。**

这句话是整个攻击的支点。它意味着：

* 如果你能确定某个位置上 8 个明文字节，你就能把这 8 个 `key` 字节**逐个独立**解出来，
  不需要管 base 是什么（base 在同一个位置上对 8 个字节是同一个值，可以直接消掉）。
* 反过来，未知数只有 `8 × len(base)` 个，而不是文件长度那么多。

---

## 5. 为什么这层加密"结构友好"

LZ4 的结构解析只依赖 token、长度扩展字节、offset。**它根本不管原样字节的内容。**

加密改了内容，没改结构。所以：

1. 密文的 LZ4 结构走向和明文完全一致；
2. 你可以"闭着眼睛沿着结构走"，一边走一边把遇到的字节解出来；
3. 走到某个位置发现结构不对（比如 offset 超出已解出的长度），说明这一步解密算错了。

这就是为什么本项目能做"已知明文"和"结构约束"两类攻击。如果换成 AES-CBC，整块密文雪崩，
这个思路立刻失效。

---

## 6. 实测：加密边界正好在 0x100

这不是猜的，是数出来的。

拿一个包，用已知的 key 解密整份文件，然后从头开始手动走 LZ4：

```
序列 0  token=16  literal=1   offset=...    ← 位置 0x10 附近，结构正常
序列 1  token=16  literal=1   offset=...    ← 正常
...
序列 7  token=...                            ← 正常
序列 8  token=...  offset=0x3A2              ← 已经越过 0x100，offset 依然合法
序列 9  token=...  offset=0x1F44             ← 非法：超过已解出的总长度
```

第 9 个 token 的起始位置是绝对偏移 `0x109`。它前面那个 token 结束在 `0x104` 左右。
把"第一个非法 token"和"第一个合法 token"之间的边界反复用不同包测，稳定落在 `0x100`。

另一个更直接的证据：本游戏的包 `data_start` 绝大多数**小于** `0x100`（实测 98.3%），
也就是说数据区的开头几十个字节落在明文区里。这些字节的 LZ4 结构完全正常，
一旦跨过 `0x100` 就开始出现非法 offset。分界线没有例外。

## 7. 加密没覆盖的地方

| 区域 | 是否加密 |
|---|---|
| 文件头（`UnityFS` 到 flags） | ❌ 明文 |
| blocksInfo 的前半段（如果它起点早于 `0x100`） | ❌ 明文 |
| blocksInfo 的后半段（超过 `0x100` 的部分） | ✅ 密文 |
| 全部数据块 | ✅ 密文 |
| 文件末尾的补齐字节 | ✅ 密文（但内容无所谓） |

"blocksInfo 后半段是密文"这一条，导致 2 297 个包在最初的实现里被当成"不是 UnityFS"
直接跳过。详见 `docs/04_PITFALLS.md` 第 11 条。

---

## 8. 还原流程

```
读文件头
  ↓
定位 blocksInfo（可能需要先 align 16）
  ↓
如果 blocksInfo 跨过 0x100：只解密它的 [0x100, 结尾) 部分
  ↓
LZ4 解压 blocksInfo，得到块表和目录表
  ↓
算 data_start，校验 data_start + Σcompressed == fileSize
  ↓
从 0x100 开始解密整个文件（分块处理，避免一次性吃满内存）
  ↓
写出 —— 得到一个标准 UnityFS，AssetRipper 可以直接吃
```

注意：**不需要重新压缩，也不需要解 LZ4**。解密后的文件本来就是一个合法的 UnityFS，
里面的数据块还是压缩状态，只是不再是密文了。

这个性质很重要：它让还原变成了"一次线性扫描 + 一次写盘"，20 GB 的数据几分钟就能跑完。

---

## 9. 怎么验证你实现对了

三条独立检查，任何一条不过都说明有问题：

1. **布局等式**：`data_start + Σ(块压缩长度) == 文件长度`。
   这条只依赖包头，与解密无关。它过了，说明头部解析对了。

2. **逐块 LZ4 解压**：每个数据块都能完整解出 `uncompressedSize` 字节。
   这条过了，说明密钥对了。本项目对 36 673 个包做了这个检查，**0 失败**。

3. **第三方实现交叉验证**：把产物交给 UnityPy 解析，能读出对象。
   这条过了，说明产物是"真正的"UnityFS，而不是"看起来像"。

本项目三条全做了，见 `docs/09_VERIFICATION.md`。

## 10. 为什么密钥不进代码，也不从网上拿

第一版工具里，`base` 是写成常量的：

```csharp
public static ReadOnlySpan<byte> DefaultBaseKey => [0x53, 0x2B, 0x46, 0x31, ...];
```

能跑，但这是错的：

1. **它是个会过期的常量。** 游戏更新后 `base` 变了，旧程序不会报错，而是安静地解出垃圾——
   结构能过、LZ4 校验会失败、用户看到的是一堆"解析失败"的包，而不是"密钥过期了"。
2. **一个常量意味着一次重新编译。** 换个密钥要改代码、重新 build、重新分发，而这件事本来
   只是"换一个字符串"。
3. **常量是死的，问题变成"谁去更新它"。** 真正需要的是"值可以单独更新"这条通道。

第二版把常量换成了一个 URL，启动时 `GET` 下来。这样确实不用重新编译了，但代价是：多了一个
必须有人维护的托管地址，多了一次网络请求，而且——**把一个本来就能算出来的值，变成了需要外部
提供的输入**。这个值是上一节那套方程解出来的，游戏文件里所有解题材料都在，没有任何理由让它
依赖第三方。

所以现在的做法是：**每次需要时从本地文件重算**。`SZB_Asset_Decryption.Core.Keys` 下的三个文件干这件事，
流程在 [`docs/11_BASE_KEY_SOLVER.md`](11_BASE_KEY_SOLVER.md)。

`XorKeystream` 里没有任何密钥常量，`RestoreOptions.BaseKey` 默认是空数组，空数组时
`RestoreService.Run` 直接抛异常拒绝运行——**宁可什么都不做，也不要写出一堆半加密的文件**。

代价也说清楚：

* 第一次要 20 秒左右（扫四万个包头，实际跑一遍方程）。之后走缓存，几十毫秒。
* 缓存跟着清单文件的**大小 + 修改时间**走。游戏更新，缓存自动失效，下次重算。
* 如果某一版游戏把"同内容不同起点"的包对清理干净了，这套方程就列不出来。那时程序会
  在日志里说清原因，退回手动填（`设置 → 手动指定`）。

这三条代价，比"用一个从别处拿来的值、错了还不知道"小得多。
