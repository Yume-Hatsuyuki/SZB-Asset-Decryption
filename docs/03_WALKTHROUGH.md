# 03 · 完整解题过程

按时间顺序记录，包括失败的尝试。

每一步都有编号，格式统一：

> **问题** — 我们想知道什么
> **做法** — 具体怎么做的，用了哪个脚本
> **结果** — 得到了什么
> **如果失败了** — 为什么失败，怎么绕过去

配套的 Python 脚本在 `lessons/`，那里的编号（01~08）是脚本自己的阅读顺序，
和这里按时间写的步骤号不是一回事。每个脚本在正文第一次出现时会给出完整路径。

## 第 0 步 · 先确认目标

**问题**：这个目录里到底有多少东西，都是什么？

**做法**：扫一遍全部 40 702 个文件，读前 16 字节，按魔数分类。

**结果**：

| 魔数 | 类型 | 数量 | 体积 |
|---|---|---|---|
| `UnityFS` | Unity 资源包 | 36 673 | 20.5 GiB |
| `AKPK` | Wwise 音频包 | 3 660 | 2.92 GiB |
| `CRID` | CRI 视频 | 346 | 2.80 GiB |
| `\x89PNG` | 图片 | 18 | 45.7 MiB |
| `OTTO` | 字体 | 2 | 8.1 MiB |
| 其它 | 配置表 / manifest / 一个打不开的映射表 | 3 | 5.4 MiB |

目录结构是 1024 个两字母子目录（`00` ~ `ZZ` 风格），文件名是 26 个大写 base32 字符。
**文件名不是资源名，是哈希。**

这一步的作用：确认主体是 36 673 个 UnityFS 包，共 20.5 GiB，后续工作集中在此。

## 第 1 步 · 复现失败

**问题**：AssetRipper 到底在哪一步崩的？

**做法**：直接用 AssetRipper 跑，看日志。

**结果**：

```
AssetRipper.IO.Files.Exceptions.DecompressionFailedException:
  Could not write any bytes for 'cab-b730676aac4eb825c976cf950b770e95'
  while decompressing Lz4HC.
```

即：**LZ4 解压该块，输出 0 字节**。

这不是"文件损坏"，因为如果是损坏，AssetRipper 通常会在更早的阶段报"magic 不对"或者
"版本不支持"。它已经读到了 `cab-...` 这个名字，说明**包头、块表、目录表全都解析成功了**，
它是在解**数据块**的时候崩的。

**结论**：容器结构完好，数据块内容有问题。

---

## 第 2 步 · 亲手解一遍包头

**问题**：包头是否真的未改动？

**做法**：写 `lessons/01_container/01_parse_bundle_header.py`，完全不用第三方库，手工按 `docs/01_UNITYFS_FORMAT.md`
的字段表解析。

**结果**：374 个抽样里 174 个能完整解析，并且全部满足：

```
data_start + Σ(块压缩长度) == 文件长度
```

这条等式**精确成立，误差为 0**。它同时证明了：

* 文件头字段全部读对了（否则 `data_start` 会算错）；
* blocksInfo 解压对了（否则块表是垃圾，Σ 不可能等于文件长度）；
* 没有任何字节被插入或删除（insert/delete 会破坏这条等式）。

**结论：加密原地替换字节，长度不变。**

这排除了重打包、插入壳、改格式三种可能。

---

## 第 3 步 · 找出加密边界在哪

**问题**：从第几个字节开始变成密文？

**做法**：写 `lessons/01_container/02_trace_lz4.py`。

按 LZ4 结构逐 token 前进：从数据区第一个字节开始，每步检查 `offset` 是否合法（不能超过已解出的字节数）。

**结果**：

```
序列 0 ~ 7   合法
序列 8       token 起点 0x104，offset 合法
序列 9       token 起点 0x109，offset = 0x1F44 > 已解出长度 → 非法
```

第一个非法 token 出现在 `0x109`，前一个 token 结束在 `0x104` 附近。
用几十个不同的包重复这个实验，边界稳定落在 **`0x100`**。

另一项核对：统计所有包的 `data_start` 分布。

```
ds < 0x100   33787 个（98.3%）
ds >= 0x100    589 个（1.7%）
ds 全部是 8 的倍数（因为 16 对齐）
```

98.3% 的包，数据区开头几十字节**落在明文区**。这解释了 AssetRipper 有时能读出一部分、有时完全读不出的现象：取决于 `data_start` 距 `0x100` 的远近。

**结论**：

```
[0x00, 0x100)  明文
[0x100, EOF)   密文
```

边界是**固定的绝对偏移**，与包结构无关。

## 第 4 步 · 排除未压缩块是明文的可能

**问题**：flags 低 6 位为 0 的块未压缩，这类块是否也未加密？若整包都是未压缩块，是否等于直接得到明文？

**做法**：`lessons/01_container/03_find_stored_blocks.py` 扫全部文件，找 `flags == 0` 的块。

**结果**：找到 107 个未压缩块，但它们的**熵仍然是 7.95**（满分 8.0）。

熵接近 8 说明字节分布近似均匀随机。正常未压缩的 Unity 数据不会如此（含大量 0 和重复的结构字段）。

**结论**：未压缩块**也被加密了**。加密是在压缩之后统一做的，跟块是否压缩无关。

## 第 5 步 · 确定密钥流的结构

**问题**：XOR 是肯定的（因为长度不变、结构不变）。但密钥流从哪来？

**做法**：这一步不是自己推的，是读 `wbunpacker` 的源码。

`crates/asset/src/lib.rs` 里有个 `AssetBundleDecryptor`，构造函数是这样：

```rust
const HEADER_SKIP_BYTES: u64 = 0x100;

let base_keys = base64::decode(base_keys_b64)?;
let asset_key_bytes = asset_key.to_le_bytes();
let mut keystream = vec![0u8; base_keys.len() * 8];

for (i, &base_byte) in base_keys.iter().enumerate() {
    let base_offset = i * 8;
    for j in 0..8 {
        keystream[base_offset + j] = base_byte ^ asset_key_bytes[j];
    }
}
```

**结果**：这段代码给出三条信息：

1. 跳过 `0x100` 字节（和我们实测的边界完全一致）；
2. 密钥流长度是 `base_keys.len() * 8`，即周期；
3. 周期内第 `i*8+j` 个字节 = `base_keys[i] ^ asset_key_bytes[j]`。

也就是说：

```
ks[o] = base[(o mod L) >> 3] ^ key[(o mod L) & 7]        L = 8 × len(base)
```

有了这个公式，问题变为：

> 已知 `base` 和 `key` 的**结构**，未知 `base` 的**取值**和每个文件的 `key` 的**取值**。
> 怎么求？

`base` 是全局的（所有文件一样），`key` 是每文件一个 `int64`。

另外，代码里 `asset_key: i64` 这个签名告诉我们：key 是**每个资源一个**，是数据驱动的，
所以它一定存在于某个清单文件里。

## 第 6 步 · 从 manifest 拿每文件 key

**问题**：key 在哪？

**做法**：

1. 游戏 CDN 上有一份 `assetbundle.manifest`，地址形如
   `https://<cdn>/dl/manifests/Windows/<version>/assetbundle.manifest`，直接 HTTP 200 可下载。
2. 格式是 MasterMemory + msgpack：多个 msgpack 对象首尾相接，最后 16 字节 MD5。
3. 写 `lessons/02_key/05_parse_manifest.py` 解析。

**问题一**：`msgpack.unpackb` 报 `ExtraData`。因为文件里是**多个连续的 msgpack 对象**，
不是一个大对象。要用 `Unpacker` 逐个读。

**问题二**：`Unpacker.tell()` 在部分版本上不可靠，读表数据时会错位。
最后的做法是：先读 TOC，拿到每张表的 (offset, length)，其中 **offset 是相对 TOC 结束位置的**，
然后再用 `unpackb` 精确切片。

**结果**：

```
TOC:
  asset      [      0, 2005753]
  raw_asset  [2005753,  211912]
  assetname  [2217665,    2271]
  config     [2219936,      18]
  toc_end = 78

表行数:
  asset      28609
  raw_asset   4113
  assetname    129
  config         1
```

`asset` 表每行是：

```
[name, hash, key, size, category, ...]
```

`hash` 就是 dat 目录里的文件名，`key` 就是我们要的那个 `int64`。

**验证**：随机抽 400 个文件，比对 manifest 里的 `size` 字段和本地文件实际大小 —— 100% 吻合。
这证明这份 manifest 和本地文件是同一个版本。

**问题三**：一开始只解析了 `asset` 表，漏了 `raw_asset` 表。
`raw_asset` 是另一种资源（非 UnityFS 的独立文件），也有自己的 hash 和 key。
漏掉它导致一部分文件"明明在 manifest 里却找不到 key"。

**覆盖率只有 47%。** 40702 个文件里只有 19189 个能在 CDN 这份 manifest 里找到。

第 10 步解决（本地有更精确的版本）。

## 第 7 步 · 破解 base（核心）

这是本项目唯一需要研究的部分。

> **本节讲思路，不讲实现。**
> 内容包括：为什么暴力搜索不可行、方程如何列出、零空间为什么有 256 个解。
> C# 实现、数据结构、缓存与性能见 [`docs/11_BASE_KEY_SOLVER.md`](11_BASE_KEY_SOLVER.md)。
> 只需运行结果读 11；需了解推导过程读本节。

### 7.1 为什么不能暴力搜

`base` 长度未知。按 `Lb = 1..32` 枚举，每字节 256 种取值，共 `256^Lb` 种。

即使已知长度为 11，也有 `256^11 ≈ 3.1 × 10^26` 种。

### 7.2 换个思路：把 base 当成未知数，列方程

观察密钥流的公式：

```
cipher[o] = plain[o] ^ base[(o mod L) >> 3] ^ key[(o mod L) & 7]
```

如果两个文件**用同一份明文**，但 `data_start` 不同，那么对同一个相对位置 `j`：

```
cipher_A[dsA + j] = plain[j] ^ base[iA >> 3] ^ keyA[iA & 7]      iA = (dsA+j) mod L
cipher_B[dsB + j] = plain[j] ^ base[iB >> 3] ^ keyB[iB & 7]      iB = (dsB+j) mod L
```

两式相减（XOR）：

```
cipher_A[dsA+j] ^ cipher_B[dsB+j]
    = base[iA>>3] ^ base[iB>>3] ^ keyA[iA&7] ^ keyB[iB&7]
```

`plain[j]` 消去。`keyA`、`keyB` 已知（第 6 步）：

```
base[iA>>3] ^ base[iB>>3] = cipher_A[dsA+j] ^ cipher_B[dsB+j] ^ keyA[iA&7] ^ keyB[iB&7]
```

右边全部已知。左边是**两个 `base` 字节之间的 XOR**。

**这是一个 GF(2) 上的线性方程。** 未知数是 `base` 的每一个比特，方程是"两个字节的异或等于一个已知值"。

一对包、连续 8 个 `j`，就能给出 8 个方程。包对越多，方程越多。

### 7.3 怎么找"同明文"的包对

**难点是不知道哪些包的明文相同。**

第一版尝试（`11_known_plaintext_probe.py`（已归档））：直接按"密文前 N 字节相同"分组。
结果只有 199 个样本、1 个组，数量不足。

第二版（`12_linear_algebra_probe.py`（已归档））：按 `data_start` 和块的解压长度分组，
找到 557 个组、4537 个样本，其中 4 个组里存在"前缀相同但 `data_start` 不同"的包对。

第三版（`13_same_plaintext_test.py`（已归档））做了一个 **L 无关的判据**：

对候选对 A、B，计算

```
R[j] = cipher_A[dsA+j] ^ cipher_B[dsB+j] ^ keyA[(dsA+j) mod 88 & 7] ^ keyB[(dsB+j) mod 88 & 7]
```

如果两个包真的用同一份明文，那么按上面公式，`R[j]` 必须等于
`base[a] ^ base[b]`。而 `base` 只有 11 个字节，`a`、`b` 都以 8 个位置为步长变化，
所以在**每 8 个连续的 j 内，`R[j]` 应该是同一个值**（因为同一组 `base` 字节对）。

判据：**检查 `R[j]` 在每 8 步的块内是否恒定。**

**结果**：大部分候选对的"不恒定率"在 8.5% ~ 78% 之间。存在一批不恒定率只有 8.5% 的**可信对**。

8.5% 的残差来自两个包的 `data_start` 不同，压缩流局部存在差异（LZ4 的 offset 值不同）。这是正常噪声，不是判据错误。

### 7.4 高斯消元，用"有没有解"反推 base 长度

**问题**：`Lb` 是多少？不知道 `Lb` 就不知道未知数有几个。

**做法**（`lessons/02_key/06_solve_base_linear.py`）：对每个候选 `Lb` 从 1 试到 60，
把方程排成矩阵，做 GF(2) 高斯消元，看**方程组是否矛盾**。

* 如果 `Lb` 猜错了，方程之间的关系是乱的，消元到最后会出现 `0 = 1` 这种矛盾行；
* 如果 `Lb` 猜对了，方程自洽，消元能正常结束。

**结果**：

```
Lb = 1..10    → 方程组矛盾
Lb = 11       → 自洽！秩 80 / 88，零空间维 8
Lb = 12..21   → 方程组矛盾
Lb = 22       → 自洽（= 2 × 11）
Lb = 33       → 自洽（= 3 × 11）
...
```

只有 **11 的倍数**才自洽，最小的正解是 **11**。

随机数据几乎不可能碰巧自洽，因此该判据有效。`Lb = 22/33/...` 也自洽，因为它们是同一周期的高倍表示。

**所以 `len(base) = 11`，周期 `L = 88`。**

### 7.5 零空间：为什么有 2^8 个解

秩 80，未知数 88 个比特，所以有 `88 - 80 = 8` 个自由变量，`2^8 = 256` 个解。

为什么会有自由度？因为方程全是 `base[a] ^ base[b] = R` 这种形式，
**把所有 `base` 字节同时异或同一个常数 C，所有方程仍然成立**。这是至少 1 个自由度。
剩下 7 个来自"方程没覆盖到的字节关系"。

**做法**：求出特解，再枚举零空间的 256 个组合，得到 256 个候选 `base`。

### 7.6 用 LZ4 闭环挑出真的

**问题**：256 个候选里哪个是真的？

**做法**：拿一个有 key 的包，用每个候选 `base` 去解密数据块，做完整的 LZ4 解压。
只有真解能解出**恰好 `uncompressedSize` 字节**，且块与块之间数据衔接正常。

LZ4 解压对密钥错误敏感：错一个比特，解出长度不对或中途 offset 非法。

**结果**：256 个候选里**恰好 1 个**通过。

```
base (hex)    = 53 2b 46 31 e4 a7 b9 47 3e 7c fb
base (base64) = UytGMeSnuUc+fPs=
```

**验证**：随机抽 400 个带 key 的包，做完整的逐块 LZ4 校验 —— **400 / 400 通过，0 失败**。

密钥至此确定。

### 7.7 两个实现错误

**错误 A：零空间回代写错，解空间不含真解。**

第一版的高斯消元，求零空间基向量时没有累积下三角的贡献，导致算出来的"解空间"
根本不包含真解。表现是：256 个候选全部 LZ4 失败。

定位方法：构造一个**已知答案的合成包**（自己用已知 base 加密一个真包），
跑求解器，看能不能还原出已知的 base。

修好后的写法是：按主元**升序**回代，并且用
`bin(others & v).count('1') & 1`（即"这一行里其它变量的贡献的奇偶"）来定主元的值。
修完之后，合成包立刻解出，而且和真值**完全一致**：

```
真值在解空间: True
base 解: 8d6cbe3ec37675aac9346c   （合成包用的假 base）
```

**错误 B：`block0_ok()` 的相位错误。**

辅助函数 `block0_ok` 把 `cipher[ds:ds+n]` 切片后直接传入解密函数。
但解密函数假设输入**从文件偏移 0 开始**，于是它把切片的第 0 字节当成了文件偏移 0。

结果：`[0x100)` 的判定错了，密钥流的相位也错了，所有候选都被判成失败。

这个 bug 是**用合成包自检时发现的**：`verify_bundle`（整文件解密）通过，`block0_ok`（切片解密）失败，两者矛盾。检查后确认是切片假设。

**结论**：只解一段的函数必须在接口中显式传入绝对偏移，不能默认从 0 开始。
`docs/04_PITFALLS.md` 第 4 条。

## 第 8 步 · 剩下 53% 的文件没有 key

**问题**：manifest 只覆盖 47%，其余 21 513 个文件没有 key。

### 8.1 三个关键事实

先把能确定的东西列出来：

**事实 1：`data_start` 全部是 8 的倍数。**
因为 `data_start = Align16(...)`，16 的倍数当然是 8 的倍数。实测 8000 / 8000 全部成立。

**事实 2：98.3% 的包 `data_start < 0x100`。**
所以数据区的开头几十个字节落在**明文区**，不需要密钥就能看到。

**事实 3：绝对偏移 `0x100` 处的 key 字节下标是 0。**

算一下：`0x100 = 256`，`256 mod 88 = 80`，`80 & 7 = 0`。
所以 `0x100` 到 `0x107` 这 8 个字节，对应的 key 字节下标依次是 `0,1,2,3,4,5,6,7`。

而 `80 >> 3 = 10`，所以这 8 个字节用的 `base` 字节**全都是 `base[10]`**，同一个值。

### 8.2 于是：8 个明文字节 → 8 个密钥字节

```
plain[0x100 + t] = cipher[0x100 + t] ^ base[10] ^ key[t]        t = 0..7
```

移项：

```
key[t] = cipher[0x100 + t] ^ plain[0x100 + t] ^ base[10]
```

**`base` 已知，`cipher` 已知（读文件就有），只要知道 `plain[0x100..0x108)` 这 8 个字节，
就能直接算出完整的 8 字节 key。**

不需要搜索或枚举。

### 8.3 这 8 个明文字节的来源

它们是 `data_start` 之后某处的 LZ4 压缩流内容。

**同类资源的压缩流开头高度相似**，例如 `Card/Materials/*.ab` 的块开头前几十字节相同。

**做法**：从 18 841 个已知 key 的文件里，采集"绝对偏移 `0x100` 处的 8 字节明文"，做成模板池。

**结果**：42 种模板，高度集中：

```
 94 次  1600010016160b00
 94 次  1600010016160b00  （不同 ds 分组）
 30 次  1600010016160b00
 20 次  1600010016160b00
  9 次  1600010016160b00
  5 次  1600010015160a00
```

前 8 字节多为 `16 00 01 00 16 16 0b 00`。

**做法**：对每个缺 key 的文件，用每个模板算出一个候选 key，然后做 LZ4 校验。
假的 key 会在第一个数据块就解不出正确长度。

**结果**：解出 14 615 个（69%）。

### 8.4 换偏移继续扩

约 900 个无法匹配，原因是 `data_start` 靠后，`0x100` 处的字节落在压缩流的不同位置。

**做法**：把采集点从 `0x100` 扩大到 `0x100 ~ 0x4000` 共 80 个位置，每个位置各采一批模板。
模板池从 42 种增至 **204 种**。

再补一轮密集偏移（`0x100 + 8i`，i < 64），又加 93 个。

**结果**：累计反推 **15 499** 个文件。

### 8.5 扩池：把新解出来的并入模板池

剩余 36 个，原模板池中没有可匹配的模板。

**做法**（`22_expand_pool.py`（已归档））：把已经解出来的 15 499 个文件的明文也采进模板池，
池子规模翻倍，再攻一次。

**结果**：剩下 **2 个**。

99.99%（34 374 / 34 376）的 key 都拿到了。

### 8.6 这条路上废掉的方案

**废案 1：无密钥 LZ4 结构 DFS**（`06_solve_keystream.py`（已归档））

思路：LZ4 结构只依赖 token/offset/长度，让求解器枚举每个 token 的值，用 `offset <= 已解长度` 剪枝，推进到文件末尾。

**失败原因**：分支因子太大。每个 token 有 256 种可能，每个 offset 有几千种可能。
即使加入强剪枝（`d > 255*r` 丢弃、`d < r-1` 丢弃），L = 8/16/24/32 全部预算耗尽，无解。

**废案 2：已知 key 求 base 的 LZ4 DFS**（`10_solve_base.py`（已归档））

思路：key 已知，仅 base 未知，用 LZ4 结构约束搜索 base 的比特。

**失败原因**：`Lb <= 8` 全部无解，`Lb = 11` 时状态空间爆炸。这条路后来被线性代数取代了。

**废案 3：双胞胎匹配**（`17b_diag_twin.py`（已归档））

思路：密文前缀相同的两个包，明文和密钥流相同，key 也应相同，可直接复用。

**失败原因**：**密文相同 ≠ keystream 相同。**
密文 = 明文 ^ keystream。两个包密文前缀相同，只能推出"明文 ^ keystream 相同"，
推不出"keystream 相同"。如果明文不同，keystream 也不同。

这是把密文相等当成密钥相等。修正后该方案作废。

**废案 4：单字节 / 双字节 XOR 暴搜**（`lessons/02_key/04_cipher_stats.py`）

假设：只 XOR 一个固定字节。

**失败原因**：熵统计显示密文熵 7.95，单字节 XOR 不改变熵。暴搜 256 种和 65536 种，全无命中。

**废案 5：从 exe / dll 里挖 base 常量**

`GameAssembly.dll` 有 199 MB，grep 了 `manifest`、`AssetBundle`、`base_keys`、
`Wizard2`、`ManifestAsset` 等关键词，全是噪声。
`il2cpp_data/Metadata` 目录是空的，元数据疑似被移除。

**结论**：base 不在明文常量中。

## 第 10 步 · 缺失的 2 297 个包（两处错误）

### 10.1 问题：blocksInfo 跨越加密边界

**现象**：`247EJXELQAJPOJSBVGTTGTMIMM` 等 2 297 个包，`parse_bundle` 直接抛异常。

**排查**：

```
头部长度 0x2C → flags & 0x200 成立 → align16 → blocksInfo 从 0x30 开始
ciSize = 295 → blocksInfo 覆盖 0x30 ~ 0x157
data_start = 0x160
```

`0x157 > 0x100`。**blocksInfo 的后半段（`0x100 ~ 0x157`）是密文。**

老的解析器假设 blocksInfo 全是明文，直接 LZ4 解压 → 失败 → 被归类为"不是 bundle"。

**修复**：解析 blocksInfo 时，如果它跨过 `0x100`，先把 `[0x100, 结尾)` 那段用 key 解一次，
再 LZ4。

解完之后：

```
nblk = 43
data_start = 0x160
data_start + Σ compressed = fileSize    ✓ 精确成立
```

**这类包一共 2 297 个，全部修复。**

### 10.2 问题：本地已有一份精确版本的 manifest

修复后任务数变为 36 673，仍有 3 000 多个因无 key 跳过。

**排查**：在分类非 UnityFS 文件时，发现 `dat/UX/UXFIK5GBEOF7EJNVAIOHLLNKFVUCZZMC`
是个 2.85 MB 的 msgpack，TOC 里是 `asset` / `raw_asset` / `assetname` / `config` ——
**这就是 manifest 本体**，游戏自己下载了一份存在本地。

**和 CDN 那份对比**：

| | CDN 下载的 | 本地这份 |
|---|---|---|
| 大小 | 2.22 MB | 2.85 MB |
| `asset` 表行数 | 32 722 | **36 673** |
| 和本地文件数匹配 | 47% | **100%** |

本地这份的 `asset` 表行数**正好等于本地 UnityFS 文件数**。

**修复**：改用本地 manifest。结果：

* 密钥覆盖率 **43% → 100%**
* 之前解不开的 2 个包直接通过
* 17~23 号那批反推脚本从此变成备用方案

**结论**：游戏会把 manifest 存在磁盘上。
`docs/04_PITFALLS.md` 第 12 条。
