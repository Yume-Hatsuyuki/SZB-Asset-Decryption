# 11 · 运行时求解 base 密钥

`docs/03` 第 7 步讲推导过程。这一篇讲程序中的实现，以及把 Python 实验代码改写成 C# 时遇到的问题。

代码在 `src/SzbTool.Core/Keys/`：

| 文件 | 职责 |
|---|---|
| `BundleProbe.cs` | 把四万个包压成"求解需要的几个字段"，并算出内容指纹 |
| `BaseKeySolver.cs` | 配对、列方程、高斯消元、枚举、LZ4 闭环 |
| `BaseKeyDerivation.cs` | 串起来：找清单 → 采集 → 求解 |
| `BaseKeyCache.cs` | 把结果连同依据一起记住，清单变了就作废 |

---

## 1. 输入与输出

**输入**：一个 `dat` 目录。别的什么也不要。

**输出**：若干字节（本版本是 11 个）和一组可审计的计数：

```
34,373 个包 · 33 对同明文 · 9,058 个窗口 · 秩 80 · 零空间 8 · 试了 84 个候选
```

这行数字是故意打印的。它让"这个值是怎么来的"变成一个可以核对的事实，而不是一句"程序算的"。

**不需要的输入**：任何已知明文、任何内存读取、任何调试器、任何网络、任何别人的结论。

---

## 2. 唯一的外部依赖：清单

程序自己产生不了的东西只有一样——每个包的 `int64` key。它在游戏自带的清单里：

```
<dat>/UX/UXFIK5GBEOF7EJNVAIOHLLNKFVUCZZMC
```

`AssetManifest.LocateLocal` 认它的方式不是文件名，也不是大小，而是三条硬条件：

1. 文件头不是 `UnityFS`（这一条就排除了 `UX` 目录里 99% 的内容——那个目录里绝大部分是普通包）；
2. 开头是 msgpack map；
3. TOC 里同时有 `asset` 和 `raw_asset` 两张表。

> **问题 1：按大小挑清单会挑错。**
> `UX` 目录里 `UX437CXUJN7DFLKPAOT3TFSGII` 有 1.36 MB，`UXFIK5...` 有 2.85 MB。第一版
> 按"第一个超过 1 MB 的文件"选，选到了前者，然后报 `TOC 不是 msgpack map`。
> 正确的判据只能是"能不能解析出上千条记录"。

## 3. 阶段一：把包压成探针

对每个文件只读文件头，得到一个 `BundleProbe`：

```csharp
DataStart   // 数据区起点
Key         // 从清单来的 int64
ContentId   // 内容指纹
BlockCount  // 块数
TotalUncompressed
FirstBlockType
```

**内容指纹里刻意不包含**：压缩后块大小、blocksInfo 大小、`data_start`、文件名。
原因是**这些字段在"同一内容重新打包"时会变化**。把它们放进指纹，就永远配不上对。

指纹里放的是：`version | unityVersion | unityRevision | 总解压大小 | 每个 node 的 (offset, size)`。

> **问题 2：指纹包含块表导致配不上对。**
> 第一版把每个块的 `解压大小 + 压缩类型` 也放进了指纹。结果 34 373 个包配出 **0 对**。
> 因为重新打包时块的切分方式会变。去掉块表、只留 node 表之后，配出 35 对。

### 块表跨界的包直接放弃

`blocksInfo` 从 `0x30` 开始时，如果它比 `0xD0` 还长，尾部就落在 `0x100` 之后——那一段是密文。
解它需要 base，而 base 正是我们要算的东西。这构成循环依赖，因此这类包跳过。

本版本有 **2 300 个**这种包，占 6%。剩下的 94% 够用了。

判断方式和 `UnityFsBundle.Parse` 里一致：读头算出 `infoOffset` 和 `ciSize`，看
`infoOffset < 0x100 < infoOffset + ciSize` 是否成立。

### 数字

本机实测（40 702 个文件）：

```
可用于求解 34,373
非 UnityFS   4,022   （AKPK 音频包、USM 视频、清单本身…）
无 key           1
块表跨界     2,300
损坏             0
```

全扫一遍 **18 秒**，八线程并行。绝大部分时间花在打开文件上，不在算上。

## 4. 阶段二：配对 + 量窗口

同一个 `ContentId` 下，按 `DataStart` 分桶。不同桶之间两两配对。最多取 48 对
（`MaxPairs`）——不是越多越好，因为每对都要读 12 KB。

对每对包，从各自 `DataStart` 读 6 KB，按 8 字节步进，算：

```
R = cA[j+t] ^ cB[j+t] ^ keyA[(oA+t) & 7] ^ keyB[(oB+t) & 7]     t = 0..7
```

**如果两个包真的同明文**，`R` 恒等于 `base[a] ^ base[b]`，而 8 个连续字节落在同一个
`>>3` 桶里，`a`、`b` 不变，所以 8 个 `R` 必须完全一样。8 个都一样却纯属巧合的概率是
`2^-56`。

**如果不同明文**，`plain[j]` 不会约掉，`R` 就是随机噪声，8 个不可能全一样。

所以这个检验本身既是"找对"，也是"排除错"，不需要事先知道谁和谁同内容。

> **问题 3：`data_start` 常为 `0x80`，前 128 字节是明文。**
> 本版本绝大多数包的 `data_start` 是 `0x80` 或 `0xA0`，意思是"数据区从 128 开始，但加密从
> 256 才开始"。第一版直接按 `data_start < 0x100` 把这些包全排除了，可用包从 34 372 掉到
> 566，然后一对都配不出来。
> 正确做法：包照收，只在**窗口层面**检查 `绝对偏移 >= 0x100`。
>
> 同一问题在"解一个块"时同样存在：块起点在 `0x100` 之前时，块内前一段是明文，
> 不能 XOR。C# 的 `XorKeystream.Apply` 已经处理了（`absoluteOffset < HeaderSkip` 时跳过），
> 但 Python 复现脚本第一版漏了，表现是"方程解对了，256 个候选全过不了 LZ4"。

一对包 6 KB ≈ 750 个窗口，通过率通常 90% 以上（剩下的是压缩流局部差异）。
48 对里能留下 30~35 对，合计 9 000~10 000 个窗口。

## 5. 阶段三：按长度试解

对每个候选长度 `Lb`（2..64），周期 `L = 8 × Lb`，把所有窗口变成方程：

```
ai = (oA mod L) >> 3
bi = (oB mod L) >> 3
base[ai] ^ base[bi] = R      →  8 条比特方程
```

`ai == bi` 时左边恒为 0，所以 `R` 必须是 0；不是 0 就说明这对包不同明文，整对作废。

方程按 `(ai, bi, R)` 去重——同一个 `(ai, bi)` 会被上百个窗口重复给出，不去重会有几十万行。

### 高斯消元

未知数是 `8 × Lb` 个比特，最多 512 个，用 `ulong[]` 位向量装。主元按最高位索引，消元过程
就是标准的 GF(2) 消元。**矛盾行**（左边消干净了右边还是 1）说明这个长度不对，直接排除。

本机结果：

```
Lb=11  自洽   方程   528  秩  80  零空间  8
Lb=22  自洽   方程  1056  秩 160  零空间 16
Lb=33  自洽   方程  1584  秩 256  零空间  8
```

11 的倍数都自洽，因为它们是同一个周期的不同写法。取**零空间最小的**先试，平手取最短的——
所以总是 `Lb=11` 先中。

方程条数和窗口数每次随机抽样会浮动，但**秩 80 / 零空间 8 稳定不变**。这本身就是个信号：
如果某次跑出来秩是 79 或 81，说明配对出了问题。

### 回代

特解按主元**升序**回代：

```
x[hb] = rhs ^ parity(coeff & solution)
```

因为消元后每个主元行的最高非零位就是主元自己，所以其它非零位都更小，升序处理时它们已经定好了。

零空间基向量也一样：对每个自由变量，把该位置 1，然后**按主元升序**逐个补上需要的位。

> **问题 4：零空间回代只看自由变量，忽略已累积的向量。**
> 第一版写成了 `if (others >> fv) & 1` —— 只看自由变量那一位，忽略其它已经补上的位。
> 表现是 256 个候选**全都不在解空间里**，LZ4 一个都过不了。
> 正确写法是 `parity(coeff & v)`，用当前累积的 `v` 算奇偶。

## 6. 阶段四：让 LZ4 挑

秩 80 / 88 意味着 8 个自由度，256 个候选。这不是实现缺陷，是方程本身丢掉了这个信息：
所有方程都是 `base[a] ^ base[b] = 常数`，**把 11 个字节同时异或同一个值，方程全都还成立**。

所以只能验。挑一个"块表在明文区、第一块是 LZ4"的包（这种包能直接解析块表，不需要 base），
对每个候选：

1. 用候选解第一块的密文；
2. LZ4 解压；
3. 要求解出来的长度**恰好等于块表声明的 `uncompressedSize`**。

错一个比特，LZ4 要么中途 offset 非法、要么解出长度不对。256 个候选里通常**第 84 个**通过。

验证只用一个包、一个块，足够了——这个判据的错误通过率低到可以忽略。想更保险可以让它多验
几个包，但没必要：`restore --verify` 本来就会逐块校验每一个产物。

## 7. 缓存

`%LOCALAPPDATA%\SzbTool\base-key.json`：

```json
{
  "DatRoot": "E:\\...\\Persistent\\dat",
  "ManifestPath": "E:\\...\\dat\\UX\\UXFIK5GBEOF7EJNVAIOHLLNKFVUCZZMC",
  "ManifestSize": 2848733,
  "ManifestWriteTicks": 639295942514228078,
  "BaseKeyHex": "532b4631e4a7b9473e7cfb",
  "ManifestEntries": 42119,
  "Probes": 34373,
  "Pairs": 33,
  "DerivedAt": "2026-11-07T10:19:14.6189067+08:00"
}
```

文件里存的是**算出来的结果 + 依据**，不是"某人填的密钥"。三条失效条件：`DatRoot` 变了、
清单路径变了、清单大小或修改时间变了。任何一条不满足，就当缓存不存在，重算。

删掉这个文件永远安全，最坏结果是多花 20 秒。

---

## 8. 这个方法什么时候会失效

诚实写在这里：

* **需要"同内容、不同起点"的包对。** 本版本有 35 对。如果某个版本把重复包清理干净了，
  方程列不出来——程序会在日志里明说"找不到包对"，然后要求手动指定。
* **需要清单里的 key 准确。** key 错了，`R` 不会有恒定段，同样报"没有包对通过检验"。
* **块表跨界的包用不上。** 它们需要 base 才能解析，而 base 正是待求量。本版本占 6%，
  不影响。
* **只适用于这个算法。** 换个加密方案（比如换成 AES、或者周期不是 8 的倍数），这套方程
  就不成立。这一条不是缺陷，是边界。

## 9. 性能与优化空间

可以，但收益不足：

* 扫描用八线程，瓶颈是打开四万个文件（NTFS 元数据），不是 CPU。加线程收益递减。
* 求解本身（48 对 × 750 窗口 × 64 个长度 + 消元 + 256 次 LZ4）**不到 1 秒**。
* 缓存是主要优化手段：第二次启动几十毫秒。

若需进一步提速，可行方向是"只扫一部分目录"——因为包对是稀疏分布，扫 5 000 个包
也大概率能找到 3~5 对。但那样失败时会给出误导性的"找不到包对"，不如全量扫描。
