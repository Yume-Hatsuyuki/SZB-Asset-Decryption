# 09 · 验证

"解出来了"和"解对了"是两件事。这一章讲怎么证明是后者。

---

## 1. 三层验证，从便宜到贵

|---|---|---|---|
| L1 结构 | 包头解析是否正确 | 微秒 | 36 673 / 36 673 |

## 2. L1：布局等式

```
data_start + Σ(每个块的 compressedSize) == 文件长度
```

这条等式**只依赖包头和块表**，和解密无关。

它同时验证了：头字段读对了、blocksInfo 解压对了、对齐规则对了、没有多算或少算字节。
误差必须是 **0**，不能是"差不多"。

实测：36 673 个包里 36 673 个精确成立。

| 结果 | 含义 |
|---|---|
| 等式成立 | 头部解析链路正确 |
| 差几十字节 | 对齐规则错（大概是把 `align 16` 漏了或错位） |
| 差很多 | blocksInfo 解压失败，块表是垃圾 |

**这条检查用于尽早失败（early fail）**：如果它不成立，后面所有步骤都不用做了。

---

## 3. L2：逐块 LZ4 长度校验

对每个数据块：

```
解密 → LZ4 解压 → 检查长度 == uncompressedSize
```

**为什么这一条能判定密钥对错**：

* LZ4 块没有魔数，也没有校验和；
* 用错误的密钥解出来的数据，会被当成"一个立即结束的序列"，解出 0 字节或一小段；
* 长度对上的概率约等于随机命中的概率，可以忽略。

所以"长度恰好等于 `uncompressedSize`"是一个**几乎不可能巧合**的判据。

实测：36 673 个包、共约 250 万个块，**0 失败**。

**这一条也是本项目所有"候选密钥筛选"的基础**：
反推密钥时每算出一个候选，就跑一次这个检查，通过了才算数。

## 4. L3：第三方实现交叉验证

**为什么要第三方**：自己写的解析器可能和自己的加密器共享同一个错误假设，
于是"自洽但不正确"。必须用一个**独立实现**去读产物。

选的是 **UnityPy**：纯 Python，和 AssetRipper 是两套完全独立的代码。

```python
import UnityPy
UnityPy.config.FALLBACK_UNITY_VERSION = "2022.3.62f2"

env  = UnityPy.load("some.ab")
objs = list(env.objects)
print(len(objs), [o.type.name for o in objs])
```

### 试验设计

三组对照：

| 组 | 输入 | 预期 | 实际 |
|---|---|---|---|
| **A 对照组** | **原始加密的 dat 文件** | 全部失败 | **0 / 20 通过** |
| B 还原产物（随机 400 个） | 解密后的 `.ab` | 全部成功 | **400 / 400 通过，22 111 个对象** |
| C 反推密钥产物（300 个） | 只靠模板反推 key 的产物 | 全部成功 | **300 / 300 通过，15 720 个对象** |

**A 组验证测试方法本身有效。**
如果 A 组也能通过，那说明测试毫无意义——因为加密文件不该能读出对象。

A 组结果与最初遇到的现象一致：

```
AssetRipper.IO.Files.Exceptions.DecompressionFailedException
```

只是这次是 UnityPy 报的，措辞不同，本质相同。

### B 组样本

```
400 个产物，全部解析成功
总对象数 22 111
```

读出的对象名字都是真的：

```
Texture2D:104741110
Sprite:bnr_web_crystal_iOS
Sprite:utx_ic_battlefest_team_16
Mesh:ms_w01_d067_light01_em_no
TextAsset:talk3d_scenario_text_7
```

### C 组为什么单独测

C 组的产物来自"反推密钥"路线，和 B 组（manifest 给 key）是两条独立的路径。
单独测是为了确认**反推出来的 key 是真 key，而不是"能让 LZ4 长度对上但内容是错的假 key"**。

```
300 个产物，全部解析成功
总对象数 15 720
```

如果反推的 key 有错，LZ4 长度检查大概率能拦住，但不排除极少数"长度巧合正确、内容错位"的情况。
L3 检查覆盖这一剩余风险。

## 6. 反向检查：确认加密文件解不出来

这一步容易被跳过，但不能跳。

如果一个"验证程序"对加密文件和明文文件**都**返回成功，那它什么都没验证。
所以每次跑 L3，都要带一组**已知应该失败**的输入。

```python
# 必须失败的那一组
原始 dat 文件 → UnityPy → 期望抛异常
```

实测 20 个，20 个都抛 `DecompressionFailedException`。
测试方法有效。

## 8. 已知限制

诚实地列出来：

1. **游戏更新会改变 manifest 版本**。`base` 不一定变，但 manifest 要重新拿。
   跑一次验证就知道：如果 400/400 还通过，就不用重算 base。

2. **`unityVersion` 被抹成 `5.x.x`**。第三方工具需要显式设 fallback（`2022.3.62f2`）。
   AssetRipper 自己有版本推断，通常不受影响。

3. **`Persistent/meta` 是 SQLite3MC 加密库**，本项目没有分析。
   它不影响资源还原。

4. **`WwiseIdMapping.bytes` 打不开**。766 KB，高熵，不是已知压缩格式（zlib/lzma/bz2 都失败）。
   推测是加密或私有编码，不影响音频还原（`DIDX` 里的 id 直接就是文件名）。

5. **语音和配置表的语义映射没有做**。能导出 `wem id`，但"这个是哪张卡的语音"
   需要读游戏的 MasterMemory 表，超出本项目范围（`wbunpacker` 做了这部分）。

## 9. 复现步骤

想自己验证一遍：

```powershell
# 1. 还原
SZB_Asset_Decryption.Cli restore --dat "D:\...\Persistent\dat" --out "D:\restored"

# 2. 逐块校验（会打印失败数）
SZB_Asset_Decryption.Cli verify --dat "D:\...\Persistent\dat" --sample 400

# 3. 第三方交叉验证
pip install UnityPy
python lessons/03_verify/07_validate_restored.py "D:\restored" 400
```

第三步会打印每个文件的"对象数 / 类型分布"，并且自动跑一组"原始加密文件"作为对照。
